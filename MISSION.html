Memo to future me

agent-terraform — Mission & Direction

Started July 2026 · Living document — update when direction changes, not when code changes

Make every internal API agent-consumable: analyze backend services from whatever exists (code, wiki, tribal knowledge), decide honestly whether an agent can use them safely, and generate the serving layer — MCP servers and Agent Skills — that lets agents do real work against them.

Why this exists

We have many internal web services. They work fine for humans and for other services, but they were never designed for agents: endpoints are too granular, descriptions say what but never when, errors assume a human developer is reading them, and nothing marks which operations are destructive. Pointing an agent at a raw API produces an agent that confidently does the wrong thing.

Wrapping each API by hand doesn't scale and doesn't accumulate. What scales is a pipeline: extract a normalized spec once, score it, and generate every serving format from that one spec. When an API changes, re-analysis is a diff, not a redo. That's the "terraform" in the name — declarative input, agent-facing infrastructure out.

Where this fits: gravity and the domain picture

gravity (ai-workspace) is the agent workspace — it defines and manages domains: the bounded contexts agents operate in. agent-terraform is the supply line underneath it. For each domain gravity defines, this repo makes that domain's backend services consumable: 

gravity (ai-workspace)          agent-terraform (this repo)
─────────────────────           ───────────────────────────
defines domains        ◄─────►  onboards each domain's services
manages agents                  spec.yaml  → readiness gate
consumes the layer     ◄──────  → MCP servers + Agent Skills

The contract between the two is the serving layer: gravity's agents mount the MCP servers and load the skills; they never see raw backends. When onboarding gravity's own services later, they go through the same pipeline as everything else — no special path.

What this project is — and is not

IsIs not
A repeatable pipeline run interactively with Claude Code skills A fully automated CI converter (maybe later, not now)
An honest assessor — red APIs get a remediation list, not a wrapper A universal adapter that pretends every API is fine
A curator — tools are intents and workflows A 1:1 endpoint-to-tool mapper (OpenAPI converters exist already)
A registry that accumulates specs, scores and serving layers A runtime platform, gateway or auth broker — gravity's territory

Principles (don't renegotiate these casually)

  • Spec in the middle. One extraction front-end (code + docs → spec.yaml), many generation back-ends. Every new output format reads the spec; nothing reads the backend twice.
  • Tools ≠ endpoints. Workflows become single server-side tools; destructive operations are annotated and confirm-gated.
  • Readiness is a gate, not a report. Green generates. Yellow generates with documented compensations. Red stops — the deliverable is the remediation list for the owning team.
  • Never guess. Unknowns are recorded as gaps in the spec and surface as "known unknowns" in generated skills, so agents don't bluff through them.
  • Secrets stay in env vars. Specs and generated code name variables; they never contain values.

Direction — phased, checkpoint at each phase

Phase 1 — Prove the pipeline (now)

  • Onboard the first real service end-to-end (candidate: a gravity/ai-workspace service, or any small Python backend).
  • Expect to revise docs/spec-format.md and the rubric after the first real contact — the format was designed on paper.
  • Done when: one service is green/yellow, its MCP server runs, and an agent completes a real task through it.

Phase 2 — Onboard the domain(s)

  • Work domain-by-domain as gravity defines them; onboard each domain's key services (Python + Spring).
  • Registry becomes the source of truth for "what can agents touch, and how safely."
  • Feed remediation lists back to owning teams; track whether scores improve.

Phase 3 — Standard, maybe automation

  • If the rubric holds up, promote it: "agent-consumable" becomes a definition teams design against, not a score they receive.
  • Only then consider CI automation (re-analyze on service change). Automating earlier would freeze a format that hasn't earned it.

Success at ~6–12 months

The key internal services are agent-ready: onboarded through the pipeline, scored green or yellow, and served via MCP + skills that gravity's agents actually use. Concretely: the registry lists them, none of them required hand-written one-off wrappers, and a new service can be onboarded in under a day.

Notes to future me

  • Resume point: open this repo in Claude Code, say onboard <service>, code at <path>, docs at <path>. The skills carry the process; this memo carries the intent.
  • Read first: docs/spec-format.md (the contract), then services/registry.yaml (current state).
  • Open questions (answer through Phase 1, not upfront):
    • Is one MCP server per service right, or will gravity want one gateway per domain? The spec format supports either; don't decide until gravity's mounting story is concrete.
    • How do yellow-compensations age — do they get removed when a team fixes the backend, and who notices?
    • Where do generated skills get distributed — copied into gravity, or does gravity read this repo directly?
  • Guardrail: if you find yourself hand-editing a generated server, stop — fix the spec or the generator skill instead. Hand edits are how the pipeline dies.
